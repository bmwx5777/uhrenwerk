# UHRENWERK — e-commerce часов

Next.js 16 (App Router) · React 19 · TypeScript strict · Tailwind CSS v4 · PostgreSQL

## Запуск с нуля

Нужны Node.js 20+ и Docker (для локального Postgres).

```bash
# 1. Зависимости
npm install

# 2. Переменные окружения
cp .env.example .env.local

# 3. Свой ключ подписи сессий — в .env.local, строка BETTER_AUTH_SECRET
openssl rand -base64 32

# 4. База: контейнер, миграции, демо-данные
npm run db:up
npm run db:migrate
npm run db:seed

# 5. Сервер
npm run dev          # http://localhost:3000
```

Секреты между разработчиками передавать не нужно: для локальной работы
каждый генерирует свой `BETTER_AUTH_SECRET`, а параметры базы в
`.env.example` указывают на контейнер из `docker-compose.yml`.
Файл `.env.local` в репозиторий не попадает и попасть не должен.

### Доступ в админку

Зарегистрируйтесь на сайте обычным способом, затем выдайте себе роль:

```bash
npm run user:admin -- ваш@email
```

Админка — `/admin`. Посторонним она отвечает 404, а не 403: незачем
сообщать о существовании раздела тому, у кого нет к нему доступа.
Если вы вошли и всё равно видите 404 — роль не выдана.

### Письма в разработке

Без `RESEND_API_KEY` письма не отправляются, а печатаются в консоль
сервера. Ссылка для сброса пароля и инструкции по оплате ищутся там же.

## Правила проекта

- Цена **никогда** не приходит от клиента: сервер заново читает её из БД перед созданием платежа.
- Деньги хранятся в минорных единицах (центах) как `integer`.
- Валидация любого внешнего ввода — Zod, на сервере.
- Дизайн-токены — только в `src/app/globals.css` (`@theme`), никаких hex-кодов в компонентах.
- Тем две. Светлая — основная (значения в `@theme`), тёмная переопределяет
  те же семантические токены в `:root[data-theme="dark"]`. Системная настройка
  `prefers-color-scheme` намеренно не учитывается: светлая тема — облик
  магазина, тёмная включается только кнопкой. Компоненты про тему
  не знают: они используют только семантические имена (`bg-surface`, `text-muted`),
  поэтому новый экран поддерживает обе темы без единой правки.
- Хардкод палитры (`bg-void-900`, `text-steel-300`) в компонентах — ошибка:
  в другой теме это станет чёрным пятном. Исключение одно — затемнение позади
  модального окна, оно тёмное в обеих темах.
- Страница пагинации каноническая сама себе (`/catalog?page=2`), а каталог
  с фильтрами помечен `noindex, follow`: сочетаний фильтров бесконечно много,
  но ссылки на товары с них обходить нужно. Поэтому фасеты **не** закрыты
  в `robots.txt` — закрытую там страницу поисковик не скачивает и пометку
  `noindex` не прочитает.
- `lastModified` товара в карте сайта берётся из `updatedAt`, не из
  `publishedAt`: иначе смена цены не заставит поисковик переобойти страницу.
- Список брендов просят и шапка, и каталог, поэтому `listBrandsWithCounts`
  обёрнут в `cache()` — за одну отрисовку это один запрос, а не два.
- Похожие модели (`getRelatedProducts`) берутся одним запросом с сортировкой
  по булевым выражениям: та же категория → тот же бренд → в наличии → новее.
  Три последовательных запроса дали бы тот же порядок втрое дороже.
- Способы оплаты на витрине рисуются из того же `PAYMENT_METHODS`, что и
  страница оплаты. Карты и крипта помечены `available: false` и показываются
  с пометкой «скоро» — так витрина не может пообещать способ, которого нет
  в оформлении заказа. Когда провайдер выбран, достаточно поднять флаг.
- Колонки подвала на десктопе не оборачиваются в `<details>`: браузер прячет
  содержимое закрытого `<details>` сам, и никакой CSS этого не отменяет.
  Аккордеон только для мобильного, разметки две, список ссылок общий.
- Поиск в шапке и страница поиска идут через один `listProducts`, поэтому
  подсказки не могут разойтись с выдачей. Слово запроса ищется и в текстовом
  индексе товара, и в названии бренда: `search_vector` — генерируемая колонка
  таблицы товара, бренд в неё попасть не может.
- Выбор темы хранится в localStorage, а не в cookie: cookie пришлось бы читать
  в корневом layout, и все страницы стали бы динамическими. Атрибут ставит
  синхронный скрипт в `<head>` (`lib/theme.ts`) — иначе страница моргает.
- Направление «Ателье»: тёплая бумага, графит и латунь (`brass-500` в тёмной
  теме, `brass-700/800` в светлой — светлая латунь на бумаге нечитаема).
  Премиальность делает не яркий акцент, а отделка: `.hairline-frame`,
  `.corner-marks`, `.rule-indices`, `.rule-fade`, `.section-index` и зерно
  бумаги на body в светлой теме. Новые экраны собираются из этих же классов.
- Шрифты — Playfair Display (заголовки и крупная цена), Geist (интерфейс),
  Geist Mono (референсы и серийные номера);
  все три с кириллицей, иначе русский интерфейс рассыпается.
- Границы **элементов управления** — `border-border-control` (3,14:1), а не
  `border-border` (1,25:1): WCAG 1.4.11 требует 3:1 для видимого контура кнопки,
  поля и выбираемой карточки. `border-border` — только декоративные разделители.
- Цены в базе — **нетто**. Витринную цену считает `lib/pricing.ts`, и та же формула
  повторена в SQL (`services/catalog.ts`) для фильтра и сортировки по цене.
- `loading.tsx` не ставим над маршрутами, которые могут отдать 404: Suspense-граница
  отправляет ответ раньше, и `notFound()` приходит со статусом 200.
- Проверка доступа — всегда в серверном коде (`requireUser()` в layout).
  `src/proxy.ts` только смотрит на наличие cookie и не является защитой.
- Запросы к данным пользователя всегда содержат `userId` в условии —
  идентификатор из формы сам по себе ничего не открывает.
- Цена не хранится в корзине: она читается из базы при каждом показе
  и пересчитывается при создании заказа.
- НДС считается на единицу товара, затем умножается на количество
  (`lineDisplayCents`) — иначе сумма строк не сходится с итогом.
- Вся арифметика заказа — в `lib/order-math.ts`. Одна функция обслуживает
  и предварительный расчёт, и создание заказа: разойтись они не могут.
- Резерв товара делается условным UPDATE (`WHERE status = 'available'`),
  а не «прочитал — проверил — записал»: только так два одновременных
  заказа на последний экземпляр не пройдут оба.
- Переходы статусов заказа перечислены явно (`ADMIN_STATUS_TRANSITIONS`)
  и меняют склад в той же транзакции: «оплачен» списывает резерв,
  «отменён» снимает.
- Роль администратора проверяется в серверном коде при каждом вызове
  (`requireAdmin()` в layout и в каждом действии), а не только в proxy.
- Цвета текста выбираются по контрасту, а не на глаз: все уровни проходят
  WCAG AA (4.5:1), границы полей ввода — 3:1 по WCAG 1.4.11. На цветной
  подложке используются отдельные, более тёмные варианты цвета.
- Цена в структурированных данных считается той же функцией, что и цена
  на странице: расхождение видимой и разметочной цены поиск считает
  нарушением.
- Тесты покрывают чистую логику (деньги, налог, разбор URL). Запросы
  к базе проверяются прогоном по живой базе — моки повторяли бы наши же
  предположения о поведении Postgres.
- Платёжные провайдеры подключаются через один интерфейс
  (`server/payments/types.ts`): добавить способ оплаты — значит добавить
  файл в `providers/` и строку в реестр.
- Срок резерва зависит от способа оплаты: перевод идёт дни, карта —
  минуты. Просроченные резервы снимает задача по расписанию.
